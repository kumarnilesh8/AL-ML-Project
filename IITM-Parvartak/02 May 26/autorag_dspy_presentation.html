PART I · MOTIVATION

RAG works until it doesn't

A naive RAG pipeline has at least 14 hyperparameters spread across 6 stages. Tune one, the others shift. Hand-engineering each is a combinatorial nightmare.

01 — INGESTION

Chunking strategy

Token vs. recursive vs. semantic. Window size 256 / 512 / 1024. Overlap 0–50%. Each shifts retrieval distribution.

02 — INDEX

Embedding choice

BGE, E5, OpenAI, Cohere, Voyage. Different geometries, different recall ceilings.

03 — RETRIEVAL

Hybrid weights

BM25 vs. dense. Top-k. RRF k-constant. Query rewriting on/off.

04 — RERANK

Cross-encoder?

Cohere rerank, BGE-reranker, ColBERT. Latency-vs-recall tradeoff.

05 — PROMPT

Template format

Few-shot count. Citation style. Refusal scaffolding. Order of context.

06 — GENERATION

Model + decoding

Sonnet vs. Opus vs. open. Temperature. Reasoning budget. Self-consistency.

The combinatorial space is roughly $|C| \times |E| \times |R| \times |M| \times |T| \times |G| \approx 10^7$ configurations. You cannot grid-search this by hand.

AUTORAG · CORE IDEA

AutoRAG = AutoML, but for retrieval pipelines

AutoRAG (Marker-Inc) treats a RAG pipeline as a directed graph of swappable nodes. Given an evaluation dataset $\mathcal{D} = \{(q_i, a_i^*, \text{ctx}_i^*)\}_{i=1}^{N}$, it searches the configuration space $\Theta$ for the pipeline $\pi^* \in \Pi$ that maximizes a composite metric.

Optimization formulation
$$ \pi^* \;=\; \arg\max_{\pi \in \Pi}\;\; \mathbb{E}_{(q,a^*) \sim \mathcal{D}}\Big[\, \mathcal{M}\big(\pi(q),\; a^*\big) - \lambda\,\mathcal{C}(\pi)\,\Big] $$

where $\mathcal{M}$ is the quality metric (faithfulness, answer-correctness, semantic similarity), $\mathcal{C}(\pi)$ is the cost (latency, $/query, tokens), and $\lambda$ trades quality for cost.

The five AutoRAG primitives

N1
QueryExpansion
HyDE, multi-query, query decomposition
N2
Retrieval
BM25, dense, hybrid, ColBERT
N3
PassageReranker
Cross-encoder, RankGPT, FlashRank
N4
PassageFilter
Threshold, recency, percentile
N5
PromptMaker → Generator
Template + LLM + decode params

AUTORAG · INGESTION

Chunking is retrieval geometry

A chunk $c$ is a contiguous span of tokens from a document. The chunking function $\phi: \mathcal{D} \to \{c_1, c_2, \ldots\}$ defines the unit of recall. Three regimes dominate:

StrategyFunctionStrengthWeakness
Token (fixed) $\phi_\tau(d) = \{d[i\cdot s : i\cdot s + w]\}$ Predictable, dense recall Splits sentences, boundary errors
Recursive Split on $[\backslash n\backslash n, \backslash n, ".", " "]$ in priority Respects structure Variance in chunk size
Semantic Boundary at $\cos(e_i, e_{i+1}) < \tau$ Topical coherence Embedding-cost at ingest
Late chunking Embed full doc → pool spans Global context preserved Requires long-context encoder 
# AutoRAG YAML — chunker search space
chunker:
  modules:
    - module_type: llama_index_chunk
      chunk_method: [Token, Sentence, SentenceWindow, Semantic_llama_index]
      chunk_size: [256, 512, 1024]
      chunk_overlap: [0, 24, 50]
      add_file_name: ko

AUTORAG · RETRIEVAL

Hybrid retrieval, then a cross-encoder

Reciprocal Rank Fusion (RRF)
$$ \text{RRF}(d) \;=\; \sum_{r \in R} \frac{1}{k + \text{rank}_r(d)}, \qquad k = 60 \text{ (canonical)} $$

Used to fuse BM25 and dense retrieval into a single ranking, robust to score-scale differences.

Cross-encoder rerank score
$$ s(q, d) \;=\; \sigma\big(\mathrm{MLP}([\text{CLS}]\;\text{Encoder}([q\,;\,d]))\big), \qquad \text{sort } d \text{ by } s $$

Bi-encoders embed $q$ and $d$ independently (fast, lossy). Cross-encoders attend $q$↔$d$ jointly (slow, accurate). Typical pattern: bi-encoder retrieves top-100, cross-encoder reranks to top-5. 

# AutoRAG retrieval + rerank stage
retrieval:
  modules:
    - module_type: bm25
      bm25_tokenizer: [porter_stemmer, ko_kiwi]
    - module_type: vectordb
      vectordb: default
      embedding_model: [openai, BAAI/bge-m3, intfloat/multilingual-e5-large]
    - module_type: hybrid_rrf
      weight: [40, 60, 80]

passage_reranker:
  modules:
    - module_type: pass_reranker
    - module_type: koreranker
    - module_type: upr
    - module_type: rankgpt
    - module_type: flag_embedding_reranker
      model_name: [BAAI/bge-reranker-v2-m3]

AUTORAG · GENERATION

Prompts are parameters

In AutoRAG, the prompt template itself is part of the search space. The generator node accepts a list of templates and a list of LLMs; the search algorithm picks the cartesian-product winner under the metric.

prompt_maker:
  modules:
    - module_type: fstring
      prompt:
        - "Answer using ONLY the passages below.\n\n{retrieved_contents}\n\nQ: {query}\nA:"
        - "You are an ESG analyst. Cite passages by [n].\n\n{retrieved_contents}\n\nQuestion: {query}"
    - module_type: long_context_reorder
    - module_type: window_replacement

generator:
  modules:
    - module_type: llama_index_llm
      llm: [openai, anthropic, vllm]
      model: [gpt-4o-mini, claude-sonnet-4-6, Qwen/Qwen2.5-7B-Instruct]
      temperature: [0.0, 0.3]
      batch: 16
Insight: the order of retrieved passages matters. long_context_reorder places highest-relevance passages at the head and tail to mitigate the lost-in-the-middle effect (Liu et al., 2023).

AUTORAG · METRICS

What does "better" mean, formally?

AutoRAG evaluates two surfaces — retrieval and generation — with composable metrics. The pipeline-level objective is a weighted sum (or hierarchical filter).

Retrieval metrics

Recall@k, Precision@k
$$\text{R@}k = \frac{|\mathcal{R}_k \cap \mathcal{R}^*|}{|\mathcal{R}^*|}, \quad \text{P@}k = \frac{|\mathcal{R}_k \cap \mathcal{R}^*|}{k}$$
Mean Reciprocal Rank
$$\text{MRR} = \frac{1}{N}\sum_{i=1}^{N} \frac{1}{\text{rank}_i^*}$$
nDCG@k
$$\text{nDCG@}k = \frac{1}{\text{IDCG}_k}\sum_{i=1}^{k} \frac{2^{\text{rel}_i} - 1}{\log_2(i+1)}$$

Generation metrics

BLEU / ROUGE-L (lexical)
$$\text{ROUGE-L} = \frac{(1+\beta^2)\,R\,P}{R + \beta^2 P}$$
Semantic similarity
$$\text{Sem} = \cos\!\big(E(\hat{a}), E(a^*)\big)$$
Faithfulness (RAGAS)
$$\text{Faith} = \frac{|\text{claims}(\hat{a}) \models \text{ctx}|}{|\text{claims}(\hat{a})|}$$

AUTORAG · SEARCH

How AutoRAG searches the pipeline space

Naive grid search is $|\Theta|$-expensive. AutoRAG uses a greedy node-wise search: each node's best variant is selected against the per-node metric while downstream nodes are held to a default. This reduces complexity from $\prod_n |M_n|$ to $\sum_n |M_n|$.

Greedy node-wise selection
$$ \pi^*_n \;=\; \arg\max_{m \in M_n}\; \mathcal{M}_n\!\Big(m \circ \pi^*_{1:n-1} \circ \pi^{\text{default}}_{n+1:N}\Big), \quad n = 1, \ldots, N $$

Per-node metrics differ: retrieval nodes use Recall@k / nDCG, generation nodes use semantic similarity + faithfulness.

Search algorithms supported

AlgorithmCostOptimalityWhen to use
Greedy (default)Linear in module countLocal optimumMost production cases
Grid$\mathcal{O}(\prod_n |M_n|)$GlobalSmall spaces, research
RandomTunable budgetProbabilisticQuick first cut
Bayesian (Optuna)Sample-efficientAsymptotic globalExpensive eval, long runs

PART II · DSPY

DSPy: "programming, not prompting"

Stop hand-engineering brittle prompt strings. Declare what you want as a typed signature; let DSPy compile the prompt — including few-shot demos, instructions, and chain-of-thought scaffolds — against a metric on real data.

THE PROBLEM

Prompt brittleness

Swap GPT-4o → Claude → Llama and your handcrafted prompt loses 10–30 points. Re-tune by hand. Repeat for every task.

THE INSIGHT

Prompts are parameters

Treat instructions and demonstrations as learnable. Define modules with clear input/output contracts. Optimize the parameters automatically.

THE INTERFACE

Signature → Module → Optimizer

A signature is a typed I/O spec. A module is a callable LM program. An optimizer (teleprompter) tunes the program against a metric.

THE OUTPUT

A compiled program

Portable across LMs. Re-compile in minutes when you swap models. Versioned, diffable, testable.

DSPY · SIGNATURES

Signatures: typed contracts for LM calls

A Signature declares input fields, output fields, and a docstring instruction. DSPy uses this to construct the prompt template — and later, to optimize it.

import dspy

# Inline form
qa = dspy.Predict("context, question -> answer")

# Class form (preferred for production)
class RAGAnswer(dspy.Signature):
    """Answer the question using ONLY the provided context.
    Cite passages by their bracketed index. Refuse if context is insufficient."""

    context: list[str] = dspy.InputField(desc="retrieved passages")
    question: str     = dspy.InputField()
    answer:   str     = dspy.OutputField(desc="≤3 sentences, cite as [1]")
    citations: list[int] = dspy.OutputField(desc="passage indices used")

predict_qa = dspy.ChainOfThought(RAGAnswer)
result = predict_qa(context=ctx, question=q)
print(result.answer, result.citations, result.reasoning)
The docstring becomes the system instruction. Field names become prompt slots. Field types control parsing. This is the entire surface area you write — DSPy generates the prompt.

DSPY · MODULES

Modules compose into programs

DSPy modules are PyTorch-flavored: subclass dspy.Module, declare predictors in __init__, define forward. They compose freely.

class RAGProgram(dspy.Module):
    def __init__(self, k=5):
        super().__init__()
        self.retrieve = dspy.Retrieve(k=k)
        self.refine_query = dspy.ChainOfThought("question -> refined_query")
        self.generate = dspy.ChainOfThought(RAGAnswer)

    def forward(self, question):
        rq  = self.refine_query(question=question).refined_query
        ctx = self.retrieve(rq).passages
        out = self.generate(context=ctx, question=question)
        return dspy.Prediction(answer=out.answer, citations=out.citations, ctx=ctx)

# Built-in predictor types:
# - dspy.Predict         (single-pass)
# - dspy.ChainOfThought  (adds `reasoning` field)
# - dspy.ProgramOfThought (executes generated Python)
# - dspy.ReAct           (tools + reasoning loop)
# - dspy.MultiChainComparison  (self-consistency)

What DSPy tracks for each predictor

  • Instruction — the textual task description (mutable by optimizers)
  • Demonstrations — few-shot examples (selected/synthesized by optimizers)
  • Format hints — output schema directives
  • Adapter — how the signature is rendered for a specific LM (Chat, JSON, completion)

DSPY · OBJECTIVE

A metric is a differentiable surrogate we can't differentiate

DSPy metrics are arbitrary Python functions $\mu: (\text{example}, \text{prediction}) \mapsto \mathbb{R}$ (or $\{0,1\}$). They can call LMs, run code, or check exact match. The optimizer's job is to find a program that maximizes their expectation.

Compilation as expected-utility maximization
$$ \theta^* \;=\; \arg\max_{\theta \in \Theta}\; \frac{1}{|\mathcal{D}_{\text{train}}|} \sum_{(x,y) \in \mathcal{D}_{\text{train}}} \mu\!\big(y,\; \pi_\theta(x)\big) $$

where $\theta$ collects all instructions and demonstrations across all predictors in the program. $\Theta$ is discrete and high-dimensional, so we cannot use gradients — hence teleprompters (search-based optimizers). 

def faithfulness_metric(example, pred, trace=None):
    # LM-as-judge: are all answer claims entailed by ctx?
    judge = dspy.ChainOfThought("context, claim -> entailed:bool")
    claims = extract_claims(pred.answer)
    score  = np.mean([judge(context=pred.ctx, claim=c).entailed for c in claims])

    # Combine with answer correctness
    correct = semantic_sim(pred.answer, example.answer) > 0.75
    return 0.6 * score + 0.4 * float(correct)

DSPY · COMPILATION

Compilation = gradient-free program synthesis

A teleprompter takes (student_program, trainset, metric) and returns a compiled program with optimized instructions and demonstrations. Conceptually, it solves a discrete optimization in three families:

FAMILY A
Demo selection
Search over which (input, output) traces to use as few-shot exemplars. Bootstrap, LabeledFewShot, KNNFewShot.
FAMILY B
Instruction synthesis
Use an LM to propose better natural-language instructions. COPRO, MIPROv2, GEPA.
FAMILY C
Weight finetuning
Distill or finetune the underlying LM on bootstrapped traces. BootstrapFinetune, Ensemble.
"Compilation" is exact: the teleprompter mutates a tree of Predict objects in-place by setting .demos and .signature.instructions, then returns the program. You can pickle the result.

TELEPROMPTER · 01 / 13
LabeledFewShot
FAMILY A · ZERO-COMPUTE BASELINE
WHAT IT DOES

Selects $k$ examples directly from the labeled trainset and attaches them as demonstrations to every predictor. No bootstrap, no search.

FORMAL
$$\mathcal{D}_{\text{demo}} = \text{sample}_k(\mathcal{D}_{\text{train}})$$
WHEN TO USE

As your "no optimization" control. Often beats unoptimized zero-shot by a wide margin and costs nothing.

CODE
from dspy.teleprompt import LabeledFewShot

tp = LabeledFewShot(k=8)
compiled = tp.compile(
    student=RAGProgram(),
    trainset=trainset
)
17 / 44
TELEPROMPTER · 02 / 13
BootstrapFewShot
FAMILY A · SELF-GENERATED DEMOS
WHAT IT DOES

Runs the (uncompiled) student program on trainset examples; keeps traces where the metric passes. Those traces — including intermediate predictor outputs — become the few-shot demonstrations.

ALGORITHM

For each $(x_i, y_i)$ in $\mathcal{D}_{\text{train}}$ until $K$ successes per predictor:

$$ \tau_i = \pi_\theta(x_i),\quad \text{accept iff } \mu(y_i, \tau_i.\text{out}) \geq \tau^* $$

The teacher LM (often a stronger model) generates these traces; the student LM uses them at inference.

CODE
from dspy.teleprompt import BootstrapFewShot

tp = BootstrapFewShot(
    metric=faithfulness_metric,
    max_bootstrapped_demos=4,
    max_labeled_demos=4,
    max_rounds=1,
    teacher_settings={"lm": opus},
)
compiled = tp.compile(
    student=RAGProgram(),
    trainset=trainset
)
PITFALL

If the teacher fails on most examples, demos are sparse. Either lower the metric threshold or use a stronger teacher.

18 / 44
TELEPROMPTER · 03 / 13
Bootstrap + RandomSearch
FAMILY A · DEMO-SET SEARCH
WHAT IT DOES

Runs BootstrapFewShot $T$ times with different random seeds (different demo subsets), evaluates each compiled program on a validation set, returns the best.

Outer loop
$$ \theta^* = \arg\max_{t \in \{1,\ldots,T\}}\; \frac{1}{|\mathcal{D}_{\text{val}}|}\sum_{(x,y) \in \mathcal{D}_{\text{val}}} \mu\!\big(y,\; \pi_{\theta_t}(x)\big) $$

$\theta_t$ is the parameter set produced by the $t$-th BootstrapFewShot run with seed $t$. 

from dspy.teleprompt import BootstrapFewShotWithRandomSearch

tp = BootstrapFewShotWithRandomSearch(
    metric=faithfulness_metric,
    max_bootstrapped_demos=4,
    max_labeled_demos=4,
    num_candidate_programs=10,   # T
    num_threads=8,
)
best = tp.compile(student=program, trainset=train, valset=val)
Reliable workhorse. Its variance comes only from demo selection — instructions are unchanged. Combine with COPRO afterwards if you have budget.

TELEPROMPTER · 04 / 13
KNNFewShot
FAMILY A · DYNAMIC PER-INPUT DEMOS

Demos are not chosen once at compile-time — they are retrieved per query from the trainset. For each test input $x$, find the $k$ nearest training examples by embedding similarity and use them as demos.

Per-query demo selection
$$ \mathcal{D}_{\text{demo}}(x) = \text{top-}k\;\arg\max_{(x_i, y_i) \in \mathcal{D}_{\text{train}}} \cos\!\big(E(x), E(x_i)\big) $$ 
from dspy.teleprompt import KNNFewShot
from dspy import Embedder

embedder = Embedder("openai/text-embedding-3-small")
tp = KNNFewShot(k=5, trainset=trainset, vectorizer=embedder)
compiled = tp.compile(student=program)
SHINES WHEN

Heterogeneous inputs (different domains, languages, styles) where a single static demo set under-fits some clusters.

WATCH OUT

Adds embedding latency at inference. Demo quality only as good as your trainset coverage in embedding space.

TELEPROMPTER · 05 / 13
COPRO
FAMILY B · COORDINATE-ASCENT INSTRUCTION OPT

COPRO (Coordinate Prompt Optimization) optimizes instructions only. For each predictor in the program, it generates a population of candidate instructions, scores them, breeds the top performers, repeats for $D$ depth iterations.

Iterative coordinate ascent over instructions
$$ I_n^{(d+1)} = \text{LM}_{\text{prop}}\!\Big(\,I_n^{(d)},\; \{\mu(\pi_{I_n^{(d)}})\}_{\text{best}}\,\Big), \qquad d = 1, \ldots, D $$

For predictor $n$, propose new instructions conditioned on the best previous instructions and their scores. Keep the top breadth $B$ at each depth. 

from dspy.teleprompt import COPRO

tp = COPRO(metric=metric, breadth=10, depth=3, init_temperature=1.4)
compiled = tp.compile(
    student=program,
    trainset=trainset,
    eval_kwargs={"num_threads": 8, "display_progress": True},
)
# Total LM calls ≈ breadth × depth × |trainset| × predictors
Use COPRO when your demos are already strong (e.g. via BootstrapFewShot) and you suspect your instruction is the bottleneck. Often gains 3–8 points on top of bootstrapped demos.

TELEPROMPTER · 06 / 13
MIPROv2
FAMILY A+B · BAYESIAN JOINT OPT

Multi-prompt Instruction PRoposal Optimizer v2. The current production default. Joint Bayesian optimization over both instructions and demonstrations across all predictors.

THREE-STAGE PIPELINE
STAGE 1
Bootstrap demos
Run student → collect successful traces → demo pool $\mathcal{P}_D$
STAGE 2
Propose instructions
LM-as-proposer reads program code + dataset summary → instruction pool $\mathcal{P}_I$
STAGE 3
Bayesian search
TPE / Optuna picks (instruction, demo-set) combos for each predictor; minibatch eval
Joint search problem
$$ \big(\mathbf{I}^*, \mathbf{D}^*\big) \;=\; \arg\max_{(\mathbf{I},\mathbf{D}) \in \mathcal{P}_I^N \times \mathcal{P}_D^N}\; \mathbb{E}_{(x,y)\sim\mathcal{D}_{\text{val}}}\big[\,\mu(y, \pi_{\mathbf{I},\mathbf{D}}(x))\,\big] $$

With $N$ predictors, the search space is exponential. MIPROv2 uses a Tree-structured Parzen Estimator to model $p(\mu | \mathbf{I}, \mathbf{D})$ and propose promising configurations.

TELEPROMPTER · 07 / 13
GEPA
FAMILY B · REFLECTIVE EVOLUTION

Genetic-Pareto. GEPA (Agrawal et al., 2025) treats prompt optimization as evolutionary search guided by natural-language reflection. After each rollout, an LM critic reads the trajectory + metric and writes a textual diagnosis; that diagnosis seeds the next instruction proposal.

Reflective mutation operator
$$ I^{(t+1)} \;=\; \text{LM}_{\text{reflect}}\!\Big(\,I^{(t)},\; \tau^{(t)},\; \mu^{(t)},\; \text{rationale}^{(t)}\,\Big) $$

Where $\tau^{(t)}$ is the rollout trace, $\mu^{(t)}$ is the metric score, and rationale is the LM-judge's natural-language critique. Population maintained on Pareto front of (quality, cost). 

from dspy.teleprompt import GEPA

tp = GEPA(
    metric=composite_metric,
    auto="heavy",
    reflection_lm=opus,        # reads traces, writes diagnoses
    num_threads=8,
    track_stats=True,
)
compiled = tp.compile(student=program, trainset=train, valset=val)
GEPA shines on complex, multi-step programs (agentic flows, long-horizon RAG, code generation) where instruction quality is far from the local optimum and reflective signal is rich. Often beats MIPROv2 with fewer rollouts on hard tasks.

TELEPROMPTER · 08 / 13
SIMBA
FAMILY A+B · ONLINE STOCHASTIC

Stochastic Introspective Mini-Batch Ascent. Online optimizer that updates demos and instructions on rolling minibatches. Designed for streaming or live-data settings where the trainset grows over time.

Mini-batch update step
$$ \theta^{(t+1)} \;=\; \theta^{(t)} \;\oplus\; \Delta_{\text{rule}}\!\Big(\mathcal{B}_t,\; \mu(\pi_{\theta^{(t)}}, \mathcal{B}_t)\Big) $$

$\oplus$ denotes parameter merging (instruction concat / demo replacement). $\Delta_{\text{rule}}$ is one of append_a_demo, append_a_rule derived from the minibatch-level introspection. 

from dspy.teleprompt import SIMBA

tp = SIMBA(
    metric=metric,
    bsize=32,
    num_candidates=6,
    max_steps=8,
    max_demos=4,
    temperature_for_sampling=0.2,
    temperature_for_candidates=0.2,
)
compiled = tp.compile(student=program, trainset=trainset)

SIMBA is the right pick when you have a continuous data stream and want the program to keep adapting without full re-compilation. Lower variance than COPRO, lower cost than MIPROv2.

TELEPROMPTER · 09 / 13
BetterTogether
FAMILY A+B+C · PROMPT OPT × FINETUNE

Alternates between prompt optimization (e.g. BootstrapFewShotWithRandomSearch) and weight finetuning (LoRA on the underlying open LM). Each round of finetuning produces traces that, in turn, sharpen the next prompt-opt pass — and vice versa.

Alternating maximization
$$ \begin{aligned} \theta_{\text{prompt}}^{(t+1)} &= \arg\max_{\theta_p} \mathcal{M}\!\big(\pi_{\theta_p, w^{(t)}}\big)\\[4pt] w^{(t+1)} &= \arg\max_{w}\; \log p_w\!\big(\mathcal{T}_{\theta_{\text{prompt}}^{(t+1)}}\big) \end{aligned} $$

$\mathcal{T}$ are the bootstrapped traces; finetuning is supervised learning on those traces. Convergence is empirical, not guaranteed. 

from dspy.teleprompt import BetterTogether

tp = BetterTogether(
    metric=metric,
    prompt_optimizer=BootstrapFewShotWithRandomSearch(metric=metric, ...),
    weight_optimizer=BootstrapFinetune(metric=metric, ...),
    strategy="p -> w -> p",
)
compiled = tp.compile(student=program, trainset=trainset)
Use only when you control the underlying LM (open weights, can finetune). Distillation play: get a small open model to match a frontier teacher's behavior on your task.

TELEPROMPTER · 10 / 13
BootstrapFinetune
FAMILY C · WEIGHT-LEVEL DISTILLATION

Generates teacher traces via bootstrap, filters by metric, then runs supervised finetuning on the student LM. The result: a model where the optimized prompt is "baked in" to weights.

SFT objective on filtered traces
$$ w^* \;=\; \arg\min_{w}\; -\sum_{(x,\hat{y}) \in \mathcal{T}^+} \log p_w(\hat{y}\,|\,x), \qquad \mathcal{T}^+ = \{(x,\hat{y}) : \mu(\hat{y}, y^*) \geq \tau\} $$ 
from dspy.teleprompt import BootstrapFinetune

tp = BootstrapFinetune(metric=metric)
compiled = tp.compile(
    student=program,
    trainset=trainset,
    target="meta-llama/Llama-3.1-8B-Instruct",
    teacher_settings={"lm": opus},
    train_kwargs={"epochs": 3, "lr": 1e-5, "bsz": 8},
)

Useful when latency or unit-cost matter more than the last 2 points of quality, and you have GPU access. Pairs naturally with a downstream prompt-opt pass on the finetuned model.

TELEPROMPTER · 11 / 13
Ensemble
INFERENCE-TIME · NO SEARCH

Take $K$ already-compiled programs (different teleprompters, different seeds, different LMs) and combine their predictions. Reduces variance, often boosts robustness.

Aggregation rules
$$ \hat{y} \;=\; \begin{cases} \text{mode}(\hat{y}_1, \ldots, \hat{y}_K) & \text{majority vote} \\[4pt] \arg\max_{y} \sum_k p_k(y\,|\,x) & \text{prob. average} \\[4pt] \text{LM-judge}(\hat{y}_1, \ldots, \hat{y}_K) & \text{learned aggregator} \end{cases} $$ 
from dspy.teleprompt import Ensemble
from dspy import majority

tp = Ensemble(reduce_fn=majority, size=5)
ensemble = tp.compile(
    programs=[compiled_v1, compiled_v2, compiled_v3, compiled_v4, compiled_v5]
)
out = ensemble(question=q)
Cheap variance reduction. Particularly useful for classification-style outputs. Costs $K\times$ at inference — gate by latency budget.

TELEPROMPTER · 12 / 13
AvatarOptimizer
FAMILY B · TOOL-USING AGENTS

Specialized teleprompter for ReAct / tool-using agents. Optimizes the agent's persona instruction and tool-selection prompt by analyzing failed trajectories and proposing a richer agent identity.

Avatar update
$$ \text{Avatar}^{(t+1)} \;=\; \text{LM}_{\text{prop}}\!\Big(\,\text{Avatar}^{(t)},\; \mathcal{F}^{(t)},\; \text{tools},\; \text{goals}\,\Big) $$

$\mathcal{F}^{(t)}$ is the set of failure trajectories (where the agent timed out, looped, or hit metric < threshold). The proposer rewrites the avatar to address those failure modes. 

from dspy.teleprompt import AvatarOptimizer

tp = AvatarOptimizer(
    metric=tool_use_metric,
    max_iters=5,
    lower_bound=0.0,
    upper_bound=1.0,
)
compiled_agent = tp.compile(
    student=react_agent,
    trainset=agentic_trainset
)

TELEPROMPTERS · BUDGETING

The cost surface of compilation

Teleprompters call LMs many times. A rough order-of-magnitude formula for budget planning:

LM-call budget
$$ \text{Calls} \;\approx\; T \cdot N_{\text{pred}} \cdot \big(|\mathcal{D}_{\text{val}}| \cdot k_{\text{eval}} + k_{\text{prop}}\big) $$

$T$ trials, $N_{\text{pred}}$ predictors, $k_{\text{eval}}$ calls per evaluation (judge LMs add $\geq 1$), $k_{\text{prop}}$ proposer calls per trial.

AutoRAG chooses the pipeline.
DSPy compiles each LM stage.

They are not competitors — they live at different layers of the optimization hierarchy.

LAYERED OPTIMIZATION
┌────────────────────────────────────────────────────────────────────────┐
│  LAYER 3 · Pipeline topology    ◄── AutoRAG picks chunker, retriever,   │
│                                     reranker, prompt template, LM     │
├────────────────────────────────────────────────────────────────────────┤
│  LAYER 2 · LM stage prompts     ◄── DSPy teleprompters compile        │
│                                     query-rewriter, generator, judge   │
├────────────────────────────────────────────────────────────────────────┤
│  LAYER 1 · Token decoding       ◄── temperature, top-p, JSON mode      │
├────────────────────────────────────────────────────────────────────────┤
│  LAYER 0 · Model weights        ◄── (BootstrapFinetune / LoRA)         │
└────────────────────────────────────────────────────────────────────────┘

The unified objective

$$ \pi^* \;=\; \arg\max_{\substack{\text{topo} \in \Pi_{\text{AutoRAG}}\\ \theta \in \Theta_{\text{DSPy}}}}\; \mathbb{E}_{\mathcal{D}}\big[\,\mu(\pi_{\text{topo},\,\theta})\,\big] - \lambda\,\mathcal{C}(\pi) $$

Outer search (AutoRAG) over topologies; inner compilation (DSPy) over prompt parameters. Solved bilevel via alternating: AutoRAG fixes topo, DSPy compiles; AutoRAG re-evaluates with compiled stages.

UNIFIED STACK · CODE

A complete ESG RAG pipeline

import dspy
from dspy.teleprompt import MIPROv2

# 1. LMs
sonnet = dspy.LM("anthropic/claude-sonnet-4-6", temperature=0.0)
opus   = dspy.LM("anthropic/claude-opus-4-7", temperature=0.7)
dspy.configure(lm=sonnet)

# 2. Signatures
class RewriteQuery(dspy.Signature):
    """Rewrite a vague ESG question into a precise retrieval query."""
    question: str = dspy.InputField()
    refined: str  = dspy.OutputField()

class ESGAnswer(dspy.Signature):
    """Answer ESG questions citing only the supplied context. Be quantitative."""
    context: list[str] = dspy.InputField()
    question: str     = dspy.InputField()
    answer:   str     = dspy.OutputField(desc="≤4 sentences with [n] citations")

# 3. Program
class ESGRag(dspy.Module):
    def __init__(self):
        super().__init__()
        self.rewrite  = dspy.ChainOfThought(RewriteQuery)
        self.retrieve = dspy.Retrieve(k=5)
        self.answer   = dspy.ChainOfThought(ESGAnswer)

    def forward(self, question):
        rq  = self.rewrite(question=question).refined
        ctx = self.retrieve(rq).passages
        out = self.answer(context=ctx, question=question)
        return dspy.Prediction(answer=out.answer, context=ctx)

# 4. Compile with MIPROv2
metric = make_composite_metric(faith_w=0.6, ans_w=0.4)
tp = MIPROv2(metric=metric, prompt_model=opus, task_model=sonnet, auto="medium")
compiled = tp.compile(student=ESGRag(), trainset=esg_train, valset=esg_val)
compiled.save("esg_rag.compiled.json")

FAILURE MODE · FAITHFULNESS

Faithfulness degrades after compilation — why?

A common production observation: BLEU/ROUGE/answer-correctness rise after MIPROv2, but RAGAS-faithfulness drops. The optimizer learned to infer from limited context, which improves apparent quality but increases hallucination.

DIAGNOSIS

The metric was wrong

Pure semantic similarity rewards plausible-sounding answers. The optimizer exploits this by being more confident, even when context is insufficient.

FIX 1

Composite metric with faithfulness floor

$\mu = \alpha\cdot\text{ans} + \beta\cdot\text{faith},\quad \mu \to 0\text{ if faith} < 0.7$

FIX 2

Add a refusal predictor

Insert a can_answer:bool ChainOfThought stage. Only generate if true. Train on counterfactual "unanswerable" examples.

FIX 3

Constrained instruction

In the signature docstring, require: "If any claim is not entailed by passages, say 'context insufficient'." MIPROv2 will preserve this constraint while tuning around it.

def faith_floored_metric(ex, pred, trace=None):
    faith = faithfulness(pred, ex.context)
    if faith < 0.7: return 0.0           # hard penalty
    ans = semantic_sim(pred.answer, ex.answer)
    return 0.5*faith + 0.5*ans

DISCIPLINE · EVAL

Three datasets, never overlapping

SET 1
Train
Used inside the teleprompter (bootstrap, propose). Can be small (50–200 ex.).
SET 2
Val
Used by the teleprompter to score candidate programs. Larger (200–1k).
SET 3
Test (held-out)
Touched ONCE after compilation. The number you report.
Reusing the val set as test is the #1 source of inflated DSPy benchmarks. The teleprompter is an optimizer over val — its score on val is biased by definition.

Sanity-check checklist

  • Calibration: compiled program should beat zero-shot on test by ≥ optimizer's variance on val (3 seed runs).
  • Robustness: swap the LM at inference. If quality collapses, you over-fit to model-specific quirks.
  • Distribution shift: hold out a "domain shift" test slice (different topic, language, format).
  • Cost regression: track tokens/query as well as quality. MIPROv2 sometimes adds long demos.
  • Faithfulness floor: compute RAGAS-faith on test even if not in your composite metric.

PRODUCTION · PATTERNS

Five patterns that scale

PATTERN 01

Compile once, deploy many

Save compiled programs as JSON artifacts. Version them in git. Roll back like any other model artifact. Treat re-compilation as a CI/CD step triggered on data drift.

PATTERN 02

Two-tier LM

Strong prompt_model (Opus) for the proposer at compile time. Cheap task_model (Sonnet, Haiku) at inference. The expensive model never runs in prod.

PATTERN 03

Metric as code

Your composite metric IS the spec. Code-review it. Test it on adversarial examples. Track its agreement with human judgment.

PATTERN 04

AutoRAG → DSPy handoff

Let AutoRAG select chunker/retriever/reranker. Export the topology. Let DSPy take over for query-rewriter + generator + judge with that fixed topology.

PATTERN 05

Refusal as a first-class output

Always include a "can_answer" or "confidence" field. Compile against a metric that rewards correct refusal as much as correct answers.

PATTERN 06

Trace logging

In prod, log every predictor's full input/output. Failures become next compile's trainset. The pipeline learns from itself.

ADOPTION · ROADMAP

A 30-day path to compiled RAG

WEEK 1 — INVENTORY

Map the current pipeline

List every prompt, every LM call, every retrieval step. Tag each as a candidate predictor. Identify the bottleneck stage by manual error analysis on 50 examples.

WEEK 2 — DATA

Build train/val/test (200/300/200)

Source from prod logs, synthetic generation, or domain SMEs. Each split must be label-clean and metric-evaluable. This is the bottleneck — invest here.

WEEK 3 — SIGNATURES

Port to DSPy

Rewrite each prompt as a Signature. Compose into a Module. Verify zero-shot baseline matches old system within 2 pt. This proves portability.

WEEK 4 — COMPILE

Light → Medium → Heavy

BootstrapFewShot first. Measure lift. Then MIPROv2 medium. Measure lift. Stop if marginal. Save the compiled artifact, ship behind a feature flag.

Day 31 onwards

  • Add observability with MLflow / Langfuse autolog
  • Set re-compile cadence tied to data drift, not calendar
  • Try GEPA if program is multi-stage and MIPROv2 plateaus
  • Layer AutoRAG for retrieval-stack search if topology is uncertain
