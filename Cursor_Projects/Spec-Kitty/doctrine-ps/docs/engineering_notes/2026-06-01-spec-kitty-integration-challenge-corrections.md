## Severity corrections

### C-005 and C-006 — Upgrade to High

**Original rating**: Medium  
**Corrected rating**: **High**

These two challenges are tightly coupled and together form a footgun in onboarding scenarios:

1. `charter generate` silently drops all org pack governance selections from the charter
2. `charter sync` reinforces the empty state — once run, it overwrites any manual fix

A developer who runs both commands during first-time setup ends up with a governance-inert charter with no error, warning, or visual indicator that anything went wrong. All required directives from the org-charter are silently absent. The severity is High, not Medium, because:

- The failure mode is silent (no error, charter appears valid)
- It occurs in the highest-traffic scenario (new project setup)
- The resulting state defeats the primary value of the pack

**Workaround (stronger than originally documented)**: After manually editing `charter.md` and `governance.yaml`, commit those files with a comment block at the top:

```yaml
# ⚠ DO NOT run 'spec-kitty charter sync --force' without re-checking
# org pack directives. charter generate/sync drops pack IDs silently.
# See engineering_notes/2026-06-01-spec-kitty-integration-challenge-corrections.md
```

## Addenda — items missing from the original challenge set

### A-1: `fragment.yaml` vs `graph.yaml` — role distinction

Not stated explicitly across C-001 and C-004, but critical for authors:

| File | Role | Who edits |
|---|---|---|
| `pack/drg/fragment.yaml` | **Authored source of truth** — pack-specific nodes and edges, preserves semantic intent including `specializes_from` | Pack authors only |
| `pack/drg/graph.yaml` | **Compiled distribution artifact** — fragment merged with spec-kitty built-in DRG, relations mapped to schema enum | Generated; committed for CI and validator consumption |

**Rule**: Authors edit `fragment.yaml` only. `graph.yaml` is regenerated on each pack release. The file has been added to version control (`0cf38c67`) as the live workaround for C-001 (DRG not auto-compiled on pack assemble).

### A-2: `specializes_from` semantic mapping — intent preserved in fragment

C-003a documents that `specializes_from` is not in the compiled graph enum and is mapped to `delegates_to` in `graph.yaml`. This is intentional:

- `fragment.yaml` uses `specializes_from` to preserve the authorial intent (an agent profile that extends/specialises a built-in)
- `graph.yaml` maps it to the closest available enum value (`delegates_to` or `enhances`) during compilation
- The split is correct and should be maintained — do not "fix" `fragment.yaml` to remove `specializes_from`

**Upstream reference**: `https://github.com/Priivacy-ai/spec-kitty/issues/1583` — tracks proper enum support for `specializes_from`.

### A-3: `graph.yaml` placement convention

The validator reads `*.graph.yaml` from the `drg/` subdirectory of the pack. The canonical path is:

```
pack/drg/graph.yaml
```

This must be included in pack releases. See C-001 / C-004 fix — the file is now committed and should be regenerated by CI on each pack version bump.

### A-4: C-004 fix owner

Originally listed as "Pack CI / docs" with no concrete owner. The immediate action (now done):

1. ✅ `pack/drg/graph.yaml` committed into the doctrine repo (`0cf38c67`)
2. ⬜ Add a CI step to regenerate `graph.yaml` from `fragment.yaml` on each pack release — no `spec-kitty doctrine pack compile-drg` command exists yet; document the manual merge script until upstream support lands
